Chapter 00

Before you start

How to read this tutorial, how to open a terminal, and a small practice folder to play with.

How to read the code boxes

The dark boxes are terminal screens. Inside them:

  • A line starting with $ is something you type. Don't type the $ itself: it is the prompt, the shell's way of saying "I'm ready".
  • Lines without $ are what the computer prints back (the output).
  • Anything after # is a comment, a note for humans. The shell ignores it.
  • Words in angle brackets, like <username>, are placeholders: replace them (brackets included) with your own value.
$ echo "Hello, lab!"     # print some text
Hello, lab!
Tip

Type the commands yourself instead of using the copy button, at least for the first chapters. Your fingers learn faster than your eyes.

Opening a terminal

  • Mac: open Terminal (Cmd+Space, type "Terminal"). macOS is Unix-based, so everything here works.
  • Linux: open Terminal from your applications menu (often Ctrl+Alt+T).
  • Windows: install WSL (Windows Subsystem for Linux). Open PowerShell as administrator, run wsl --install, restart, then open "Ubuntu" from the Start menu. You now have a real Linux terminal.

Chapter 01

Unix, the shell & how we work in bioinformatics

Why we type commands instead of clicking, and what the words everybody uses actually mean.

Unix and Linux

Unix is a family of operating systems born in the 1970s. Linux is a free Unix-like system, and it runs almost every server, supercomputer and cluster in the world. macOS is also Unix underneath. When people say "learn Unix" they mean: learn to use these systems through text commands.

Terminal vs shell

These two get mixed up all the time:

  • The terminal is the window: the app that shows text and receives your keystrokes.
  • The shell is the program running inside that window. It reads what you type, runs it, and prints the result. The most common shell is bash; Macs use zsh by default, which behaves almost identically for everything in this tutorial.

Think of the terminal as a phone and the shell as the person on the other end who follows your instructions.

Why bioinformatics lives in the terminal

  • Data is big. A single sequencing run can produce hundreds of gigabytes. You can't open that in Excel, but command-line tools can stream through it line by line.
  • Tools are command-line programs. Aligners, assemblers, variant callers and phylogenetics software (BWA, SAMtools, IQ-TREE, MAFFT…) almost never have buttons. You run them by typing.
  • The heavy work happens on a cluster, a group of powerful computers you reach remotely. There is no desktop there, only a shell.
  • Everything is reproducible. A command can be saved in a script and run again next year, on new data, by someone else. Clicks can't.

A typical project

Most analyses follow the same shape: raw data comes in, gets checked and processed by a chain of tools, and results come out. Each step is a command, and the whole chain is written down in scripts.

Raw dataFASTQ reads from the sequencer
→
QC & cleaningcheck quality, trim adapters
→
Processingalign, assemble, call variants
→
Analysistrees, statistics, figures

We keep each project in its own folder with the same structure. Raw data is never edited; everything else can be regenerated from it.

my_project/ ├── data/ raw data, treat as read-only ├── scripts/ every command you ran, as scripts ├── results/ outputs produced by the scripts ├── logs/ messages from cluster jobs └── README.md what this project is and how to rerun it

File formats you will meet

Most bioinformatics files are plain text, which is why simple Unix tools work so well on them.

Chapter 02

Moving around

The file system is a tree of folders. You are always standing in one of them.

The tree

Everything starts at the root, written /. Folders (also called directories) contain files and more folders. Your personal folder is your home directory, shortened to ~.

/ the root: the top of everything ├── home/ │ └── ana/ ~ (Ana's home directory) │ └── unix_tutorial/ │ ├── data/ │ │ ├── genes.fasta │ │ ├── reads.fastq │ │ └── samples.tsv │ ├── results/ │ └── scripts/ ├── usr/ programs installed on the system └── tmp/ temporary files

Where am I? pwd

pwd means print working directory. The working directory is the folder you are "standing in" right now.

$ pwd
/home/ana

What's here? ls

$ ls                      # list the current folder
unix_tutorial
$ ls unix_tutorial/data   # list another folder without going there
genes.fasta  reads.fastq  samples.tsv
$ ls -l unix_tutorial/data   # long format: permissions, owner, size, date
-rw-r--r-- 1 ana lab 143 Sep 29 10:12 genes.fasta
-rw-r--r-- 1 ana lab 105 Sep 29 10:12 reads.fastq
-rw-r--r-- 1 ana lab 138 Sep 29 10:12 samples.tsv

The first column of ls -l starts with d for a directory and - for a normal file. The rest (rw-r--r--) are permissions: who can read, write and execute it (you, your group, everyone else).

Go somewhere: cd

cd means change directory.

$ cd unix_tutorial        # go into a folder
$ cd data                 # and deeper
$ pwd
/home/ana/unix_tutorial/data
$ cd ..                   # go up one level
$ cd ~                    # go home (plain "cd" does the same)
$ cd -                    # go back to where you just were

Absolute and relative paths

A path is the address of a file or folder. There are two ways to write one:

  • Absolute paths start with / (or ~) and work from anywhere: /home/ana/unix_tutorial/data/genes.fasta
  • Relative paths start from where you are now: if you are in unix_tutorial, the same file is data/genes.fasta

Three shortcuts appear everywhere:

SymbolMeans
~your home directory
.the current directory
..the parent directory (one level up)
Watch out

Avoid spaces and special characters in file names. my file.txt looks like two separate things to the shell. Use my_file.txt or my-file.txt. If you receive a file with spaces, put its name in quotes: ls "my file.txt".

Chapter 03

Working with files

Creating, copying, moving, deleting and peeking inside files.

Create folders and files

$ cd ~/unix_tutorial
$ mkdir test                  # make a directory
$ mkdir -p test/a/b/c         # -p creates the whole chain at once
$ touch test/notes.txt        # create an empty file

Copy: cp

The pattern is always cp <from> <to>.

$ cp data/genes.fasta test/                 # copy into a folder, same name
$ cp data/genes.fasta test/my_genes.fasta   # copy with a new name
$ cp -r test test_backup                    # -r (recursive) to copy a whole folder

Move and rename: mv

Unix has no separate "rename" command: renaming is moving a file to a new name.

$ mv test/my_genes.fasta test/genes_v2.fasta   # rename
$ mv test/genes_v2.fasta results/              # move into another folder

Delete: rm

$ rm results/genes_v2.fasta   # delete a file
$ rm -r test_backup           # delete a folder and everything inside it
$ rmdir test/a/b/c            # delete a folder only if it is empty
There is no trash bin

rm is permanent. No undo, no recycle bin. Before deleting, run ls with the same path to see exactly what will go. Beginners can use rm -i, which asks for confirmation for every file. And never run rm -rf on a path you haven't double-checked.

Look inside files

CommandWhat it does
cat filePrints the whole file. Fine for small files, a flood for big ones.
less fileOpens a scrollable viewer. Arrows or space to move, / to search, q to quit. Use this for large files.
head fileFirst 10 lines. head -n 4 file for the first 4.
tail fileLast 10 lines. tail -f log.txt keeps watching a file as it grows.
wc -l fileCounts lines (word count). Without -l it prints lines, words and characters.
$ head -n 4 data/genes.fasta
>geneA Homo sapiens
ATGGCGTACGTTAGC
>geneB Mus musculus
ATGCCGTTAGCATTA
$ wc -l data/genes.fasta
8 data/genes.fasta

Wildcards

The * matches "anything". The shell expands it into the list of matching file names before running the command.

$ ls data/*.fasta      # every file ending in .fasta
$ ls data/*            # everything in data
$ cp data/*.fast* results/    # genes.fasta and reads.fastq

? matches exactly one character: sample_?.fq matches sample_1.fq but not sample_10.fq.

Chapter 04

Commands, flags & manuals

Every program you will ever run follows the same grammar. Learn it once and any new tool becomes readable.

Anatomy of a command

$ ls -l -h data/
# program: ls    flags: -l -h    argument: data/
  • Program: the first word, what to run (ls).
  • Flags (also called options): start with a dash and change how the program behaves (-l, -h).
  • Arguments: what the program should act on, usually files or folders (data/).

Words are separated by spaces, which is why spaces in file names cause trouble.

Short and long flags

  • Short flags use one dash and one letter: -h. Several can be combined: ls -l -a -h is the same as ls -lah.
  • Long flags use two dashes and a word: --human-readable. Easier to read in scripts, can't be combined.
  • Some flags take a value: head -n 5, sort --key=2. The value comes right after the flag.

Bioinformatics tools look scary but follow the exact same grammar. For example, an alignment command:

$ bwa mem -t 8 reference.fa sample_R1.fq sample_R2.fq > sample.sam
# program: bwa, subcommand: mem, flag with value: -t 8 (use 8 threads)
# arguments: the reference and the two read files
# > sample.sam  sends the output into a file (see next chapter)

Many big tools (bwa, samtools, git, conda) have subcommands: the second word picks what part of the tool you use, and each subcommand has its own flags.

How to read the manual

You are not expected to memorise flags. Everybody looks them up, all the time. There are three places to look:

$ man ls              # the full manual page (q to quit, / to search)
$ ls --help           # short summary, printed straight to the screen
$ samtools            # many bio tools print their usage when run with no arguments
$ samtools sort       # ...and so do their subcommands
  • man works for classic Unix commands. Inside it, type / followed by a word to search, n for the next match, q to leave.
  • --help or -h works for most programs, including bioinformatics tools and Python scripts.
  • Reading a usage line: things in [brackets] are optional; things in <angle brackets> are required; ... means "one or more".
Usage: head [OPTION]... [FILE]...
#   OPTION is optional and can be repeated; so is FILE.
Tip

Paste any confusing command into explainshell.com and it breaks it down flag by flag.

How programs work: input, output, errors

Most command-line programs follow the same logic: they read input (a file, or text coming from another program), do one thing to it, and write the result to output. By default the output is printed to your screen. Error messages go to a separate channel so they don't get mixed with the results. The three channels have names you will see in documentation:

ChannelNameDefault
standard inputstdinkeyboard, or a file / another program
standard outputstdoutthe screen
standard errorstderrthe screen (errors and progress messages)

Unix is built on small programs that each do one job well. The power comes from chaining them, which is the subject of the next chapter.

Chapter 05

Pipes, redirection & grep

Save output to files and plug programs into each other. This is where the command line starts to feel powerful.

Redirection: send output to a file

$ grep ">" data/genes.fasta > results/headers.txt    # >  write (overwrites!)
$ echo "one more line" >> results/headers.txt        # >> append to the end
$ wc -l < data/genes.fasta                          # <  read input from a file
$ some_tool input.fa > out.txt 2> errors.log         # 2> sends stderr to its own file
Watch out

> silently replaces the file if it already exists. Use >> when you want to add to it. Never redirect into the same file you are reading: sort file.txt > file.txt leaves you with an empty file.

Pipes: |

The pipe (the vertical bar, usually Shift+\) takes the output of the command on the left and feeds it as input to the command on the right. No intermediate files needed.

$ grep ">" data/genes.fasta | wc -l      # how many headers = how many sequences
4
$ ls data | head -n 2
genes.fasta
reads.fastq

Build pipelines step by step: run the first command, look at the output, add the next |, look again.

Searching text: grep

grep prints every line that contains a pattern. It's probably the command you'll use most.

FlagEffect
-ccount matching lines instead of printing them
-vinvert: lines that do not match
-iignore upper/lower case
-nshow line numbers
-A 1also print 1 line after each match (-B for before)
-rsearch in every file inside a folder
Always quote the >

grep > genes.fasta without quotes is a disaster: the shell reads > as redirection and overwrites your FASTA with nothing. Always write grep ">" genes.fasta.

More small tools for tables

CommandWhat it does
cut -f 2keep column 2 of a tab-separated file (-d "," for CSV)
sortsort lines. -n numeric, -r reverse, -k 4 by column 4
uniqcollapse identical adjacent lines, so always sort first. -c counts them
tail -n +2everything from line 2 on: a quick way to drop a header
awk, sedsmall languages for editing text on the fly. Worth learning later
$ cut -f 2 data/samples.tsv | tail -n +2 | sort | uniq -c
      2 human
      2 mouse
      1 zebrafish

Chapter 06

Scripts with nano

A script is a text file full of commands. Writing your work into scripts is what makes it repeatable.

The nano editor

nano is a simple text editor that runs inside the terminal. It's on almost every system, including every cluster, so you can always edit a file even without a graphical interface.

$ nano scripts/hello.sh     # opens the file (creates it if it doesn't exist)

The shortcuts are listed at the bottom of the nano screen. ^ means Ctrl.

KeysAction
Ctrl+O, then Entersave ("write Out")
Ctrl+Xexit (asks to save if there are changes)
Ctrl+Wsearch ("Where is")
Ctrl+K / Ctrl+Ucut a whole line / paste it
Alt+Uundo

Your first script

Write this in scripts/hello.sh:

#!/bin/bash
# My first script: says hello and shows where it runs

echo "Hello from $(hostname)"
echo "Today is $(date)"
echo "I am in $(pwd)"
  • The first line, the shebang #!/bin/bash, says which program should run the file.
  • $(command) runs a command and pastes its output in place.
$ bash scripts/hello.sh        # run it with bash
$ chmod +x scripts/hello.sh    # or make it executable once...
$ ./scripts/hello.sh           # ...and run it directly

Variables and arguments

A variable stores a value. Set it with name=value (no spaces around =!) and read it with $name. Inside a script, $1, $2… are the arguments you gave when running it.

#!/bin/bash
# Usage: bash scripts/describe.sh <fasta file>
file=$1
echo "Looking at: $file"
echo "Lines: $(wc -l < "$file")"

Put variables in double quotes ("$file") so names with odd characters don't break things. Single quotes don't expand variables: '$file' prints literally $file.

Loops

A for loop repeats commands for every item in a list. This is how you process 50 samples with the same command.

$ for f in data/*.fasta data/*.fastq; do echo "$f"; wc -l < "$f"; done

The same loop written nicely in a script:

#!/bin/bash
for f in data/*
do
    echo "Processing $f"
    # the real tool would go here, e.g. fastqc "$f"
done
Good habits

Start every script with a comment saying what it does and how to run it. Add set -euo pipefail under the shebang: the script then stops at the first error instead of carrying on with broken results.

Chapter 07

The cluster & Slurm

How to ask a shared supercomputer to run your work, politely and efficiently.

What a cluster is

A cluster (or HPC, high-performance computing system) is many computers, called nodes, connected together and shared by many users.

  • Login node: where you land after ssh. It is for light things only: editing scripts, moving files, submitting jobs.
  • Compute nodes: where the real work runs. You don't log into them directly; you ask for them.
  • Scheduler: the program that receives everyone's requests and decides who gets which node and when. Ours is Slurm.
Golden rule

Never run heavy analyses on the login node. It's shared by everyone, and admins will kill your process (and send you an email). Anything longer than a minute or two goes through Slurm.

A job script

A Slurm job is a normal bash script with some special comment lines at the top, starting with #SBATCH. They tell Slurm what resources you need. Save this as scripts/count_job.sh:

#!/bin/bash
#SBATCH --job-name=count_seqs        # a name you'll recognise in the queue
#SBATCH --output=logs/%x_%j.out      # %x = job name, %j = job ID
#SBATCH --error=logs/%x_%j.err
#SBATCH --time=00:10:00              # max run time, HH:MM:SS
#SBATCH --cpus-per-task=1            # CPU cores
#SBATCH --mem=1G                     # memory
#SBATCH --partition=<partition>      # which queue; ask your admin

set -euo pipefail
echo "Job started on $(hostname) at $(date)"

bash scripts/count_seqs.sh data/genes.fasta

echo "Finished at $(date)"
$ mkdir -p logs                      # Slurm will NOT create this folder for you
$ sbatch scripts/count_job.sh
Submitted batch job 4815162
$ cat logs/count_seqs_4815162.out   # read the output once it finishes

The job starts in the folder you submitted from, so relative paths in the script are relative to there.

Watching and managing jobs

CommandWhat it does
sbatch job.shsubmit a job script
squeue -u $USERyour jobs in the queue. State PD = pending (waiting), R = running
scancel <jobid>cancel a job. scancel -u $USER cancels all of yours
sinfopartitions and how busy the nodes are
sacct -j <jobid>information about finished jobs (did it fail? how long did it take?)
seff <jobid>how much of the requested CPU and memory the job really used (if installed)
$ sacct -j 4815162 --format=JobID,JobName,State,Elapsed,MaxRSS,ExitCode

Asking for the right resources

  • Ask for too little and the job is killed: TIMEOUT (ran out of time) or OUT_OF_MEMORY.
  • Ask for too much and you wait longer in the queue and block resources others could use.
  • Test on a small subset first, check with seff what it really used, then scale up with some margin.
  • If a tool can use several cores (a flag like -t or --threads), pass it the number you asked Slurm for: --threads $SLURM_CPUS_PER_TASK.

Interactive sessions

To test commands on a compute node, ask for an interactive shell. When it starts, your prompt shows a different host name: you are on a compute node now. Type exit to give it back.

$ srun --cpus-per-task=2 --mem=4G --time=01:00:00 --pty bash

Software modules

Many clusters provide pre-installed software through modules:

$ module avail              # what exists (can be a long list)
$ module avail samtools     # search for one tool
$ module load samtools      # make it available in this session
$ module list               # what you have loaded

If a tool isn't available as a module, you install it yourself with conda (next chapter).

Job arrays: one script, many samples

An array runs the same script many times, each with a different number in $SLURM_ARRAY_TASK_ID. Use that number to pick a sample from a list.

#!/bin/bash
#SBATCH --job-name=per_sample
#SBATCH --array=1-5                  # 5 tasks, IDs 1 to 5
#SBATCH --output=logs/%x_%A_%a.out   # %A = array job ID, %a = task ID
#SBATCH --time=00:10:00
#SBATCH --mem=1G

# samples_list.txt has one sample name per line
sample=$(sed -n "${SLURM_ARRAY_TASK_ID}p" samples_list.txt)
echo "Task $SLURM_ARRAY_TASK_ID is working on $sample"

sed -n "3p" file prints line 3 of a file, so task 3 gets the third sample.

Chapter 08

Installing software: conda & pip

You rarely have admin rights on a cluster, and every tool needs specific versions of other tools. Package managers solve both problems.

The problem

Tool A needs Python 3.8, tool B needs Python 3.12, and a third one needs an old version of a library that breaks both. Installing everything in one place ends in chaos (people call it "dependency hell"). The fix is environments: separate, isolated boxes, each with its own set of tools and versions. You switch between boxes as needed.

conda

conda installs software of any language (C, Python, R, Java…) and manages environments. Bioinformatics tools are distributed through the bioconda channel, which relies on conda-forge for general libraries. A channel is simply a repository where conda looks for packages.

We recommend installing Miniforge: a minimal conda that uses conda-forge by default and includes mamba, a faster drop-in replacement (mamba install = conda install).

# one-time setup of channels (the order matters)
$ conda config --add channels bioconda
$ conda config --add channels conda-forge
$ conda config --set channel_priority strict

The everyday commands

$ conda create -n qc fastqc seqkit        # new environment "qc" with two tools
$ conda activate qc                       # step into it: the prompt shows (qc)
(qc) $ seqkit stats data/genes.fasta      # the tools are now available
(qc) $ conda install multiqc              # add more to the active environment
(qc) $ conda list                         # what's installed here
(qc) $ conda deactivate                   # step out
$ conda env list                          # all your environments
$ conda remove -n qc --all                # delete an environment
Tips

Make one environment per project or per group of related tools, not one giant environment for everything. Big environments become slow to solve and hard to update. Never install things into base.

Share and rebuild environments

$ conda env export --from-history > environment.yml   # save the recipe
$ conda env create -f environment.yml                 # rebuild it elsewhere

Keep environment.yml in your project and in git. --from-history saves only what you asked for, which rebuilds more easily on another computer.

pip

pip installs Python packages only, from PyPI. Some Python tools exist only there. The rule is to run pip inside an activated conda environment, so the package lands in that box and not in the system.

$ conda activate myproject
(myproject) $ python -m pip install <package>
(myproject) $ python -m pip list

python -m pip guarantees you use the pip that belongs to the Python you're running.

conda or pip?

SituationUse
A bioinformatics tool (samtools, iqtree, mafft…)conda (bioconda)
A Python library that exists on conda-forgeconda, to keep one manager in charge
A Python package only on PyPI or GitHubpip, inside a conda environment
Tool already provided by the clustermodule load
  • Install with conda first, pip last. If you conda-install after pip-installing, conda may overwrite things pip put there.
  • Never use sudo pip. On a cluster you don't have sudo anyway.
  • If pip complains about an externally-managed-environment, you are not inside an environment: activate one.
  • Lost? which python and which samtools tell you which copy you are actually using.

Chapter 09

Git & GitHub

Version control: a complete history of your scripts, a backup, and a way to share code.

What they are

  • Git is a program that records snapshots of a folder over time. Each snapshot is a commit, with a message saying what changed. You can compare versions and go back to any of them. It runs on your computer.
  • GitHub is a website that hosts git folders (repositories, or "repos") online. It is a backup, a place to share code with collaborators and reviewers, and often where you'll download other people's tools. GitLab and Bitbucket do the same job.

Git replaces analysis_final.sh, analysis_final2.sh, analysis_final_REALLY.sh.

The three places your changes live

Working folderfiles as you edit them
git add
→
Staging areachanges chosen for the next snapshot
git commit
→
Local historysnapshots on your computer
git push
→
GitHubthe copy online

The staging area lets you decide what goes in a commit: you might edit five files but only commit the two that belong together.

One-time setup

$ git config --global user.name "Your Name"
$ git config --global user.email "you@university.edu"   # same email as on GitHub
$ git config --global init.defaultBranch main
$ git config --global core.editor nano                   # use nano for commit messages

The daily cycle

$ cd ~/unix_tutorial/scripts
$ git init                       # turn this folder into a repository (once)
$ git status                     # what changed? run this constantly
$ git add count_seqs.sh          # stage a file (git add . stages everything)
$ git commit -m "Add script to count FASTA sequences"
$ git log --oneline              # the history, one line per commit
$ git diff                       # what changed since the last commit, line by line

git status is your best friend: it tells you what is modified, what is staged, and often suggests the next command.

Connecting to GitHub

GitHub no longer accepts your password from the terminal. The easiest way is an SSH key: a pair of files, one private (stays on your computer) and one public (you give to GitHub).

$ ssh-keygen -t ed25519 -C "you@university.edu"   # press Enter to accept the defaults
$ cat ~/.ssh/id_ed25519.pub                       # copy this whole line
# GitHub → Settings → SSH and GPG keys → New SSH key → paste
$ ssh -T git@github.com                           # test: "Hi username! You've successfully authenticated"

Do this once per computer (your laptop and the cluster each need their own key).

Then, to send a local repository to GitHub, create an empty repository on github.com (no README), and:

$ git remote add origin git@github.com:<username>/<repo>.git
$ git push -u origin main        # first push; afterwards just: git push
$ git pull                       # bring down changes made elsewhere

To start from a repository that already exists online:

$ git clone git@github.com:<username>/<repo>.git

What not to put in git: .gitignore

Git is for code and small text files. Not for sequencing data, BAMs or big results: GitHub refuses files over 100 MB, and a repo full of data becomes unusable. List what git should ignore in a file called .gitignore:

# .gitignore
data/
results/
logs/
*.fastq.gz
*.bam
.DS_Store
Watch out

Never commit passwords, tokens or unpublished data to a public repository. Once pushed, assume it's public forever, even if you delete it later.

Undoing things

SituationCommand
I messed up a file and want the last committed version backgit restore file.sh
I staged something by mistakegit restore --staged file.sh
Typo in the last commit message (not pushed yet)git commit --amend
A pushed commit broke somethinggit revert <commit> (makes a new commit that undoes it)
What did this file look like 3 commits ago?git show HEAD~3:file.sh

Commit IDs are the codes shown by git log --oneline (like a1b2c3d). HEAD means "the latest commit".

Branches, briefly

A branch is a parallel line of history. Use one to try an idea without touching your working version; merge it back if it works.

$ git switch -c new-filter     # create a branch and move to it
# ...edit, add, commit as usual...
$ git switch main              # back to the main line
$ git merge new-filter         # bring the changes in
Good habits

Commit small and often, each commit doing one thing. Write messages that say why: "Filter reads with MAPQ < 30 to remove multimappers" beats "update". Push at the end of every day: it's your backup.

A free code editor that makes writing scripts and documentation more comfortable. A companion to the terminal, not a replacement.

What it's good for

A word on the built-in terminal

VS Code has a terminal panel inside it. In our lab we prefer to keep a separate terminal window for running commands and use VS Code for reading and writing files. The reasons:

  • On the cluster, and in many situations later, there is no graphical interface. If you learn with a real terminal, you're never stuck.
  • Remote-SSH runs a small server on the cluster's login node. Some clusters restrict it; if it's unavailable, you still need ssh and nano.
  • Buttons and panels can hide what's happening. Knowing the actual commands (git add, git commit) means you understand what the buttons do.

The same applies to the git panel: handy for looking at diffs, but learn the commands first.

When you are stuck

  1. Read the error message, slowly. It usually says exactly what's wrong (No such file or directory means the path is wrong).
  2. Check where you are (pwd) and what's there (ls).
  3. Check the manual (--help, man).
  4. Search the exact error message online.
  5. Ask. Bring the command you ran and the full error message.
